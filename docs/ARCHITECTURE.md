## 주요 결정과 이유

### 1. 페이지는 요청마다 DB에서 렌더링하고, 캐시는 CloudFront 한 곳에만 둔다

- 공개 페이지(`/`, `/recipes/*`)는 `force-dynamic`으로, 요청이 오면 Postgres에서 읽어 렌더링합니다.
  응답에는 `Cache-Control: public, max-age=0, s-maxage=300`을 붙입니다([next.config.ts](../next.config.ts)).
  - **빌드할 때 DB가 필요 없습니다.** CI는 VPC 안의 DB에 접근할 수 없습니다.
  - CloudFront가 5분간 HTML을 캐시하므로, 트래픽 대부분은 서버까지 오지 않습니다.
- Next.js의 ISR이나 `use cache`를 쓰지 않은 이유: 이 캐시들은 **태스크마다 따로** 존재합니다.
  관리자가 수정한 뒤 한 태스크에서만 무효화되면, CloudFront가 다른 태스크에 남은 옛 내용을 다시 캐시할 수 있습니다.
  이를 막으려면 Redis 같은 공유 캐시가 필요한데, 비용과 운영할 대상이 늘어납니다. 캐시를 한 곳(CloudFront)에만 두면 이 문제가 생기지 않습니다.
- 관리자가 저장하면 `after()`에서 CloudFront `/*` 무효화를 요청합니다([src/lib/cdn.ts](../src/lib/cdn.ts)). 수정은 보통 1분 안에 반영됩니다.
- 캐시 키에는 쿼리스트링 전체(Next.js의 `?_rsc=`)와 `rsc`·prefetch 헤더가 들어갑니다. 그래서 HTML과 RSC 응답이 섞이지 않습니다.
  공개 경로에는 쿠키를 전달하지 않으므로, 세션 정보가 캐시에 섞여 들어갈 수 없습니다.

### 2. NAT 게이트웨이 없음

- NAT 게이트웨이는 서울 리전에서 월 $45 이상이고, AZ 두 개면 $90입니다. 대신 태스크를 public subnet에 두고 공인 IP를 줬습니다(태스크당 $3.65).
- 인바운드는 보안그룹으로 **ALB에서 오는 3000번 포트만** 허용합니다. 아웃바운드는 443(AWS API)과 5432(RDS)만 엽니다.
- ALB와 RDS는 인터넷 경로가 아예 없는 private subnet에 있습니다.

### 3. 내부 ALB + CloudFront VPC 오리진

- ALB에 공인 주소가 없으므로, CloudFront를 거치지 않고 오리진에 직접 들어오는 경로가 없습니다(WAF 우회 불가).
- 도메인이 없어서 CloudFront→ALB 구간은 HTTP입니다. 이 구간은 AWS 내부망입니다. 도메인과 인증서가 생기면 HTTPS로 바꿉니다.

### 4. 데이터베이스 계정 분리

| 계정 | 사용처 | 권한 |
|---|---|---|
| `bakery_admin` (마스터) | ops 태스크만 (마이그레이션, 시드, 관리자 생성) | 소유자 |
| `app_user` | 웹 서비스 | 테이블 DML만 (DROP/ALTER 불가) |

- 마스터 비밀번호는 RDS가 Secrets Manager에서 7일마다 교체합니다. ops 태스크는 시작할 때마다 새로 읽으므로 교체 영향을 받지 않습니다.
- 앱 비밀번호는 SSM SecureString에 저장합니다(무료).

### 5. 관리자 인증

- 비밀번호는 scrypt(N=2^15, r=8, p=3)로 저장합니다. Node 표준 라이브러리라서 네이티브 빌드가 필요 없습니다.
- 세션은 랜덤 32바이트 토큰입니다. DB에는 SHA-256 해시만 저장하고, 쿠키는 `__Host-` + HttpOnly + Secure + SameSite=Lax입니다.
- 무차별 대입은 두 겹으로 막습니다.
  - Postgres의 실패 기록: 15분 동안 같은 이메일+네트워크 5회, 같은 네트워크 20회, 같은 이메일 50회. IPv6는 /64 단위로 셉니다.
    같은 이메일·네트워크의 시도는 advisory lock으로 한 줄로 세워 처리하므로, 동시에 쏟아지는 요청도 정확히 한도까지만 통과합니다.
    최근 30일 안에 로그인에 성공한 네트워크는 이메일 전체 한도(50회)를 적용받지 않습니다. 그래서 공격자가 여러 주소로 실패를 쌓아도 관리자는 평소 쓰던 곳에서 계속 로그인할 수 있습니다.
  - WAF: `/admin` 아래 POST를 IP당 5분에 30회로 제한합니다.
- 비밀번호 검증(scrypt)은 태스크당 동시에 4개까지만 돌려서, 로그인 폭주가 페이지 응답을 막지 않게 합니다.
- `proxy.ts`는 쿠키가 있는지만 보고 빠르게 리다이렉트합니다. 실제 권한 검사는 모든 관리자 페이지와 Server Action의 `requireAdmin()`이 합니다.
- Server Action의 CSRF 방어는 Next.js가 Origin과 Host를 비교하는 방식입니다. 이를 위해 `/admin*` 경로는 viewer의 Host 헤더를 그대로 전달합니다.

### 6. 배포 안전장치

- 이미지 태그는 변경 불가(IMMUTABLE)인 git SHA입니다. ECR이 push할 때 취약점을 스캔합니다.
- 롤링 배포는 최소 100%, 최대 200%로 진행합니다. 서킷 브레이커가 실패를 감지하면 자동으로 롤백합니다.
- `deploymentId`(git SHA)로 버전 차이를 처리합니다. 배포 중 옛 화면을 들고 있던 사용자는 페이지 이동 때 새 버전으로 새로고침됩니다.
  다만 Server Action ID는 빌드마다 달라질 수 있습니다. `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`를 GitHub 시크릿으로 고정하면 ID가 유지됩니다(DEPLOY.md 5단계).
  고정하지 않으면, 배포 직후 열어 둔 관리자 화면은 새로고침 후 다시 저장해야 할 수 있습니다.
- 컨테이너는 `server-entry.cjs`로 시작합니다. 이 파일은 두 가지를 강제합니다.
  - Next.js가 `0.0.0.0`에서 대기하게 합니다. Fargate가 HOSTNAME을 덮어써도 헬스체크가 실패하지 않습니다.
  - 3xx·5xx 응답에는 `no-store`를 붙입니다. DB 장애로 난 500 페이지나 RSC 리다이렉트가 CloudFront에 5분간 캐시되지 않습니다.
- 정적 파일은 S3에 **지우지 않고 계속 쌓습니다**. 배포 중이나 직후에도 옛 HTML이 참조하는 JS/CSS가 404가 나지 않습니다.

## 트래픽 산정 (목표: 중앙대 홈페이지 수준)

- 가정: 하루 3만~10만 페이지뷰, 몰릴 때 순간 300 rps, 그 10배 스파이크까지.
- 페이지 하나당 요청은 HTML 1개와 정적 파일 약 10개입니다. 정적 파일은 100% CDN에서 나갑니다.
- HTML은 URL마다 엣지에서 5분 캐시되므로, 오리진 요청은 엣지 로케이션 수 × URL 수 × 5분당 1회 수준(초당 1건 미만)입니다.
- 오리진 처리량: 로컬 측정에서 단일 Node 프로세스가 캐시 없이 DB를 매번 조회해도 레시피 페이지를 약 240 rps(p95 100ms) 처리했습니다.
  0.5 vCPU 태스크라면 보수적으로 태스크당 60~100 rps로 봅니다. CDN 캐시가 전부 빗나가는 최악의 경우에도 6태스크로 수백 rps를 받을 수 있습니다.
- 오토스케일링: CPU 60% 또는 태스크당 분당 1200요청(오리진 기준)을 넘으면 늘리고, 범위는 2~6개입니다.
- DB 연결: 롤링 배포 중 최대 12태스크 × 풀 5 = 60으로, micro의 한도(약 80) 안입니다.

실제 수치는 `loadtest/k6-recipes.js`의 `origin` 시나리오로 측정해서 조정하세요.
